# V1 编码闭环实现

本文档记录在 V0 运行框架之上落地 V1 的实际实现：让 Agent 在受控工作区内完成一次带真实验证证据的代码修复，并能依据失败结果继续修正。目标与范围以 V1 需求为准，本文档只描述**当前源码已实现并被确定性测试覆盖**的行为。

## 1. 目标与边界

完成判定从“模型声称完成”改为“当前代码版本上存在真实退出码证据”。模型动态决定搜索、读取、修改和选择验证配置；程序固定保证访问边界、写入前置条件、真实执行与证据版本匹配。

V1 不提供：语义/向量检索、复杂重命名、二进制编辑、删除文件、自动提交/推送/PR、常驻或交互式进程、操作系统级沙箱、多 Agent 编码协作、通用自动代码评审。运行范围限定为受信任项目——受控指命令准入与生命周期管理，测试代码本身仍可执行任意逻辑。同一 `RootPath` 上并发两个编码任务在 V1 不做防护，由宿主配置避免。

## 3. 唯一的内核改动：per-tool 超时

`ToolExecutor` 默认对所有工具施加统一的 `ToolTimeoutSeconds`（生产默认 10 秒），构建与测试必然超时。新增 `IToolTimeout` 标记接口（Abstractions）：实现该接口的 contextual 工具可声明自己的超时秒数，执行器优先采用；`BoundTool` 把声明透传给内部工具。`run_verification` 依据所选 profile 中最大超时返回分钟级超时。未实现该接口的工具行为完全不变，V0 测试零回归。

进程超时**或收到用户取消**都会进入同一条有界终止流程：终止整棵进程树、等待退出确认、有界等待管道排空。超时返回结构化 `TimedOut`；用户取消在确认进程树已退出后**再**抛出取消异常（任务按 V0 语义进入中断/核实），因此取消的构建/测试不会继续运行或改文件。若无法确认终止（超时/取消两种情形），返回 `KillUnconfirmed`（验证工具据此给 `Effect.Unknown`），任务进入 Reconciliation，绝不重放、也不假定进程已死。该取消路径有独立测试（单进程 + 派生孙进程整树回收）。

## 4. A–F 与代码的对应

### A 工作区访问层

- 路径以 `ToolExecutionContext.Workspace.RootPath` 为基准统一规范化；越界相对路径、越界绝对路径、junction/symlink 绕过均被拒绝。链接检查沿路径逐段进行并**包含最终文件本身**（早期版本只对目录段检查，会漏掉指向工作区外的文件符号链接）；确实不存在的路径仍可解析（供 `create_file`）。文件符号链接的动态测试在具备 `SeCreateSymbolicLink`/开发者模式权限时真实执行拒绝断言，权限不足时显式 `SKIP`（不以 junction 冒充），同时无条件覆盖“普通文件可读、新建路径可解析”的负向用例。
- 授权来自 `Workspace.Grants`（`read`/`write`/`execute`），由宿主在任务启动时注入，工具参数不接受授权范围。写入在执行前再次检查，而非仅注册时检查。
- 单文件大小、搜索结果数量、返回长度均有上限；可靠支持 UTF-8，保留原有字节与换行形式；二进制与不支持编码得到明确失败。
- 所有拒绝均无文件副作用。

### B 定位工具

`list_files`、`search_text`（字面量；跳过构建产物等目录，规则集中可见）、`read_file`（返回内容、行号、内容哈希、截断标记）。哈希供后续 `apply_patch` 的前置条件使用。

### C 修改与改动清单

- `create_file(path, content)`：不覆盖已有文件。
- `apply_patch(path, expected_hash, old_text, new_text)`：`old_text` 必须在当前文件中**唯一**匹配；匹配 0 处或多处都拒绝并返回计数，文件不变。补丁在内存中匹配后用临时文件原子替换。提供的哈希与当前内容不符（读后被外部修改）则拒绝。
- `get_changes()`：只报告 Agent 本次任务改动（路径、前后哈希、任务/操作关联，以及每个文件**可读的 unified diff**），数据来自工作区外的 `ChangeLedger` 与写前快照，**不运行 `git diff`、不重置**，因此用户既有的未提交修改不会被冒认为 Agent 成果。diff 的“改前”取工作区外基线快照，“改后”读当前工作区并与记录哈希核对：若文件在记录之后又被改动，会显式标注 `currentDiffersFromRecord`，不把漂移后的内容当成记录时刻的差异；当前文件已删除也单独标注。
- 副作用语义按写入阶段严格区分：写入/移动前失败为 `Failed/Effect.None`（无副作用）；移动报错但磁盘确认仍是旧内容为 None；移动报错但磁盘已是新内容、或**写入确认成功后改动账本持久化失败**，为 `Failed/Effect.Unknown`（代码改变真实存在、仅记录缺失，消息携带已确认哈希，禁止盲目重放补丁）；移动结果无法判定亦为 Unknown。V1 不承诺跨文件事务；逐文件修改，部分成功如实报告。

### D 受控进程执行

结构化可执行程序与参数列表（非拼接 shell）；工作目录限定在授权工作区；stdout/stderr 同时消费避免缓冲阻塞；执行时间、输出量与日志文件大小分别受限；超时**和用户取消**都终止进程树并等待确认（见 §3）；日志写到工作区外的产物目录，不污染内容指纹。正常退出、非零退出、启动失败分别结构化表达，启动失败不会作为致命异常炸掉任务。

### E 验证工具与证据

`run_verification(profile)`：模型只选宿主允许的 profile 名（如 `build`、`unit_tests`、`regression`），命令模板、参数与验收要求由宿主配置。

每次执行计算工作区前后指纹，并产出 `EvidenceRecord`（复用 V0 的 `ToolOutcome.Evidence` / `ArtifactReference`，随操作自动归属任务与操作）：

- requirement 稳定标识为 `verification:<profile>`；
- `Passed` 与真实退出码绑定，非零退出是**可反馈的验证失败**，不是任务致命异常；
- 运行期间工作区变化（前后指纹不同）不颁发当前版本通过证据；
- profile 可配 `TestCountRegex` 与 `MinimumTests`：输出缺少测试计数标记、或计数低于下限（含零测试）都不能通过——退出码 0 不足以证明测试执行；
- 失败验证也留下证据与日志；源码再次变化后，旧通过证据的 revision 与当前版本不再匹配，完成策略自动判其失效；
- profile 命令模板变更会移动 `IVersionedTool.Version`，能力快照随之变化，旧操作自动失效。

### F 完成策略

新增 `CodingCompletionPolicy`：对每个必需 requirement，一次性按“归属本任务 + requirement 匹配 + `Passed` + 退出码 0 + **工作区 revision 等于当前版本**”筛选证据，不再先取第一条通过记录再判版本（那会让旧版本的通过证据遮蔽新版本的通过证据，导致永远要求重验）。同 revision 有多条通过记录时取最新执行结果，不由插入顺序决定。若当前版本无通过证据，则区分“从未通过（missing）”与“仅旧版本通过（stale）”给出不同反馈。只要仍有预算，返回 `CanContinue` 并把缺口回填给模型；预算耗尽或环境不允许继续时才进入等待。Server 用 `CodingRoutingPolicy` 路由：带编码必需证据的任务走编码策略，普通 echo/add 任务保持 V0 行为不变。任务启动时宿主写入必需验证要求，模型可补充验证但不能删除必需项。

## 5. 编辑→失效→重规划（重要时序）

这是接入后被测试实证、而非仅靠读码推断的行为：编辑工具只改磁盘，`task.Facts.Workspace.Revision` 在下一轮循环顶部的 `RefreshWorkspace` 才更新，而下一步的能力快照在此之前拍摄。因此**编辑之后紧接着发出的验证操作会被 V0 的失效规则拒绝一次**（无论是否与编辑同批提交），操作得到 `Operation invalidated: capability or workspace changed` 观察；模型据此在新一步重发验证，此时快照已刷新，验证才真正执行。这正符合 V1 需求“一次编辑后，旧批次中的其他调用按 V0 规则失效，模型能重新读取或规划”。端到端确定性测试显式覆盖了“被拒绝→重发→得到真实结果”的链路。

## 6. 宿主配置

`appsettings.json` 的 `Coding` 节（默认 `Enabled: false`）：

```json
"Coding": {
  "Enabled": true,
  "ArtifactDirectory": ".data/artifacts",
  "Grants": ["read", "write", "execute"],
  "RequiredVerification": ["unit_tests"],
  "IgnoredDirectories": ["TestResults"],
  "Profiles": [
    { "Name": "build", "FileName": "dotnet", "Arguments": ["build"],
      "TimeoutSeconds": 180 },
    { "Name": "unit_tests", "FileName": "dotnet",
      "Arguments": ["run", "--no-build", "--", "self-test"],
      "TimeoutSeconds": 180, "MinimumTests": 1,
      "TestCountRegex": "Tests run: (\\d+)" }
  ]
}
```

`IgnoredDirectories` 与工作区指纹共用同一 provider，验证产物目录必须排除，否则“刚通过的证据会被自己写的日志判为过期”。

## 7. 验证

确定性工程验收（脚本化假模型 + 真实临时工程 + 真实文件 + 真实测试进程），离线、不调用真实模型：

```powershell
.\scripts\verify.ps1                      # 全量：V0 回归 + V1
.\scripts\verify.ps1 -Stage v1-e2e        # 仅编码端到端
```

当前 Release 构建 0 警告 0 错误，离线测试 **56/56 通过**（V0 既有 36 + V1 新增 20）。关键 V1 阶段：

| 阶段 | 覆盖 |
| --- | --- |
| `v1-tool` | per-tool 超时覆盖默认上限 |
| `v1-workspace` | 受限读取/搜索/列举、哈希、跳过规则；越界/链接（含文件符号链接，权限不足时 SKIP）/授权/二进制/大小拒绝无副作用 |
| `v1-mutation` | create 拒绝覆盖；账本只计 Agent 改动并产出可读 diff；过期哈希与歧义补丁零副作用；唯一补丁原子替换并保留 CRLF；**写后账本故障报 Unknown 而非 None** |
| `v1-process` | 退出码、双流排空、stderr、启动失败区分；超时杀一次性进程；**用户取消回收进程及其孙进程整棵树** |
| `v1-verify` | 通过/失败证据绑定真实退出码与 revision；零测试/缺 marker 不发通过证据；运行中变更使证据失效 |
| `v1-policy` | **旧通过证据不遮蔽当前版本新证据**；missing 与 stale 反馈区分；预算耗尽转等待 |
| `v1-e2e` | 失败修复闭环（含编辑失效→重发）；提前声称完成被缺口阻止；新增回归用例被发现并暴露缺陷 |

样例工程 `examples/sample-dotnet-project/` 是零 NuGet 依赖的控制台程序，内置一个种子缺陷（`ApplyDiscount` 按绝对量而非百分比扣减），从 `tests/*.case` 数据文件读取断言，`self-test` 输出 `Tests run: N` 标记并以退出码反映结果。种子态退出 1（第二个用例失败），修正实现后 3/3 通过。**新增回归用例只需添加 `.case` 文件，无需重编译**，对应“新增回归测试”验收。

## 8. G 层真实模型验收（待模型额度恢复执行）

确定性测试证明框架能力，但不能证明模型稳定性；这一层**当前未完成**，原因是模型额度实测被阻塞（见末尾“当前阻塞”），不做任何替代性宣称。额度恢复后按下列 runbook 执行——其中**宿主命令均已离线实测**，只差模型决策这半边。

### 8.1 两类必做任务

1. **修复既有缺陷**：直接修复样例工程的种子缺陷，使现有/回归测试通过。
2. **先补回归再修复**：先新增一个能暴露原问题的 `.case` 用例（无需重编译即可被发现），观察它在缺陷态失败，再修复使全部通过——证明测试确实被发现且能暴露原问题。

样例工程 `examples/sample-dotnet-project/`：种子缺陷为 `Calculator.ApplyDiscount` 按绝对量扣减（`price - percent`），应为 `price - price * percent / 100`。`self-test` 在**首个失败用例处**返回，故种子态输出 `Tests run: 2`、退出码 1、stderr 为 `ApplyDiscount(200, 10) expected 180 got 190`；修对后跑完全部用例（当前 3 个）输出 `Tests run: 3 ... All tests passed.`、退出码 0。因此 `MinimumTests` 设为 1 即可，marker 存在且计数 ≥1 才承认执行了测试。

### 8.3 启用并启动（额度恢复后执行）

用命令行覆盖指向样例工程与有效模型端点（不把密钥写入文件），`Server:WorkspaceRoot` 必须是样例工程的**绝对路径**：

```powershell
$sample = (Resolve-Path examples/sample-dotnet-project).Path
dotnet run --project src/MiniHarness.Server -c Release -- `
  --Urls http://127.0.0.1:5080 `
  --Server:ApiKey $env:HARNESS_API_KEY `
  --Server:WorkspaceRoot $sample `
  --Model:Protocol Responses --Model:BaseUrl $env:MODEL_BASE_URL --Model:Model $env:MODEL_NAME --Model:ApiKey $env:MODEL_API_KEY `
  --Coding:Enabled true `
  --Coding:RequiredVerification:0 unit_tests `
  --Coding:Profiles:0:Name build --Coding:Profiles:0:FileName dotnet --Coding:Profiles:0:Arguments:0 build --Coding:Profiles:0:Arguments:1 -c --Coding:Profiles:0:Arguments:2 Release `
  --Coding:Profiles:1:Name unit_tests --Coding:Profiles:1:FileName dotnet `
    --Coding:Profiles:1:Arguments:0 run --Coding:Profiles:1:Arguments:1 -c --Coding:Profiles:1:Arguments:2 Release --Coding:Profiles:1:Arguments:3 -- `
    --Coding:Profiles:1:Arguments:4 self-test --Coding:Profiles:1:MinimumTests 1 '--Coding:Profiles:1:TestCountRegex=Tests run:\s*(\d+)'
```

> 注：`unit_tests` 直接用 `dotnet run -c Release`（其内部先构建），可同时暴露编译错误；如需把“构建”与“测试”拆成两个必需 profile，把 `RequiredVerification` 加上 `build` 并要求模型两者都跑。HTTP 契约：`POST /agent/tasks/commands`（Bearer `HARNESS_API_KEY`）提交 `{"kind":"Start","request":{"model":"mini-agent","messages":[{"role":"user","text":"<任务>"}]}}`，再轮询 `GET /agent/tasks/{id}` 与 `/events?follow=true` 观察工具调用、证据与终态。该编排脚本尚未在有额度环境端到端跑通，首次执行需按真实响应校正。

### 8.4 必须留存的证据与成功判据

每个任务保存：原始需求、最终 diff（`get_changes` 的 diff 或样例工程 `git diff`）、执行的 profile 与命令、退出码、日志 artifact 路径与哈希、执行前后工作区 revision、模型/工具调用次数、**失败尝试记录**（不以一次成功宣称普遍稳定）。

成功判据（任务 1 与任务 2 各自满足）：任务终态 `Completed`；完成证据的 `WorkspaceRevision` 等于完成时工作区 revision（旧 revision 证据不得放行）；最后一次 `unit_tests` 退出 0 且 marker 计数 ≥ 用例数；任务 2 必须观察到“新增用例先失败（exit 1，stderr 指向新用例）→ 修复后通过”。

## 9. 已知限制

- 进程树终止在 Windows 上为 best-effort；无法确认时进入核实流程而非假定成功。
- 补丁协议为单处唯一 `old/new` 文本匹配，单次调用不处理多处替换。
- 指纹为非加密快照基线，不提供并发隔离或不可变验证快照（后续强化）。
- 产物目前直接落盘到工作区外目录并登记 `ArtifactReference`，V1 不做独立 blob 服务。
