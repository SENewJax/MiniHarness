# V1 编码闭环实现

本文档记录在 V0 运行框架之上落地 V1 的实际实现：让 Agent 在受控工作区内完成一次带真实验证证据的代码修复，并能依据失败结果继续修正。目标与范围以 V1 需求为准，本文档只描述**当前源码已实现并被确定性测试覆盖**的行为。

## 1. 目标与边界

完成判定从“模型声称完成”改为“当前代码版本上存在真实退出码证据”。模型动态决定搜索、读取、修改和选择验证配置；程序固定保证访问边界、写入前置条件、真实执行与证据版本匹配。

V1 不提供：语义/向量检索、复杂重命名、二进制编辑、删除文件、自动提交/推送/PR、常驻或交互式进程、操作系统级沙箱、多 Agent 编码协作、通用自动代码评审。运行范围限定为受信任项目——受控指命令准入与生命周期管理，测试代码本身仍可执行任意逻辑。同一 `RootPath` 上并发两个编码任务在 V1 不做防护，由宿主配置避免。

## 2. 模块与依赖

```text
MiniHarness.Abstractions   契约（新增 IToolTimeout 标记接口，见 §3）
        ↑
MiniHarness.Coding        新增：工作区访问、定位/修改/验证工具、进程执行器、完成策略
        ↑
MiniHarness.Harness       V0 内核（ToolExecutor 识别 IToolTimeout；指纹忽略目录可配置）
        ↑
MiniHarness.Server        组合根：读取 Coding 配置，注册工具、账本、指纹、策略
```

Coding 仅依赖 Abstractions，不反向依赖 Harness，避免项目环。需要 Harness 能力的地方（完成策略的回退、工作区指纹）由 Server 在组合根显式注入。

## 3. 唯一的内核改动：per-tool 超时

`ToolExecutor` 默认对所有工具施加统一的 `ToolTimeoutSeconds`（生产默认 10 秒），构建与测试必然超时。新增 `IToolTimeout` 标记接口（Abstractions）：实现该接口的 contextual 工具可声明自己的超时秒数，执行器优先采用；`BoundTool` 把声明透传给内部工具。`run_verification` 依据所选 profile 中最大超时返回分钟级超时。未实现该接口的工具行为完全不变，V0 测试零回归。

进程超时后终止进程树并等待退出确认；无法确认终止时返回 `Effect.Unknown`，任务进入 Reconciliation，绝不重放。

## 4. A–F 与代码的对应

### A 工作区访问层

- 路径以 `ToolExecutionContext.Workspace.RootPath` 为基准统一规范化；越界相对路径、越界绝对路径、junction/symlink 绕过均被拒绝。
- 授权来自 `Workspace.Grants`（`read`/`write`/`execute`），由宿主在任务启动时注入，工具参数不接受授权范围。写入在执行前再次检查，而非仅注册时检查。
- 单文件大小、搜索结果数量、返回长度均有上限；可靠支持 UTF-8，保留原有字节与换行形式；二进制与不支持编码得到明确失败。
- 所有拒绝均无文件副作用。

### B 定位工具

`list_files`、`search_text`（字面量；跳过构建产物等目录，规则集中可见）、`read_file`（返回内容、行号、内容哈希、截断标记）。哈希供后续 `apply_patch` 的前置条件使用。

### C 修改与改动清单

- `create_file(path, content)`：不覆盖已有文件。
- `apply_patch(path, expected_hash, old_text, new_text)`：`old_text` 必须在当前文件中**唯一**匹配；匹配 0 处或多处都拒绝并返回计数，文件不变。补丁在内存中匹配后用临时文件原子替换。提供的哈希与当前内容不符（读后被外部修改）则拒绝。
- `get_changes()`：只报告 Agent 本次任务改动（路径、前后哈希、任务/操作关联），数据来自工作区外的 `ChangeLedger` 与写前快照，**不运行 `git diff`、不重置**，因此用户既有的未提交修改不会被冒认为 Agent 成果。
- V1 不承诺跨文件事务；逐文件修改，部分成功如实报告。写入已发生但结果未确认时进入未知副作用处理，不自动重复应用补丁。

### D 受控进程执行

结构化可执行程序与参数列表（非拼接 shell）；工作目录限定在授权工作区；stdout/stderr 同时消费避免缓冲阻塞；执行时间、输出量与日志文件大小分别受限；超时/取消终止进程树并等待确认；日志写到工作区外的产物目录，不污染内容指纹。正常退出、非零退出、启动失败分别结构化表达，启动失败不会作为致命异常炸掉任务。

### E 验证工具与证据

`run_verification(profile)`：模型只选宿主允许的 profile 名（如 `build`、`unit_tests`、`regression`），命令模板、参数与验收要求由宿主配置。

每次执行计算工作区前后指纹，并产出 `EvidenceRecord`（复用 V0 的 `ToolOutcome.Evidence` / `ArtifactReference`，随操作自动归属任务与操作）：

- requirement 稳定标识为 `verification:<profile>`；
- `Passed` 与真实退出码绑定，非零退出是**可反馈的验证失败**，不是任务致命异常；
- 运行期间工作区变化（前后指纹不同）不颁发当前版本通过证据；
- profile 可配 `TestCountRegex` 与 `MinimumTests`：输出缺少测试计数标记、或计数低于下限（含零测试）都不能通过——退出码 0 不足以证明测试执行；
- 失败验证也留下证据与日志；源码再次变化后，旧通过证据的 revision 与当前版本不再匹配，完成策略自动判其失效；
- profile 命令模板变更会移动 `IVersionedTool.Version`，能力快照随之变化，旧操作自动失效。

### F 完成策略

新增 `CodingCompletionPolicy`：必需证据缺失、或证据 revision 与当前工作区不匹配时，只要仍有预算，返回 `CanContinue` 并把明确缺口作为 system 反馈回填给模型；预算或环境不允许继续时才进入等待。证据的“版本匹配 + 通过 + 退出码 0”判定复用既有的证据完成策略语义。Server 用 `CodingRoutingPolicy` 路由：带编码必需证据的任务走编码策略，普通 echo/add 任务保持 V0 行为不变。任务启动时宿主写入必需验证要求，模型可补充验证但不能删除必需项。

## 5. 编辑→失效→重规划（重要时序）

这是接入后被测试实证、而非仅靠读码推断的行为：编辑工具只改磁盘，`task.Facts.Workspace.Revision` 在下一轮循环顶部的 `RefreshWorkspace` 才更新，而下一步的能力快照在此之前拍摄。因此**编辑之后紧接着发出的验证操作会被 V0 的失效规则拒绝一次**（无论是否与编辑同批提交），操作得到 `Operation invalidated: capability or workspace changed` 观察；模型据此在新一步重发验证，此时快照已刷新，验证才真正执行。这正符合 V1 需求“一次编辑后，旧批次中的其他调用按 V0 规则失效，模型能重新读取或规划”。端到端确定性测试显式覆盖了“被拒绝→重发→得到真实结果”的链路。

## 6. 宿主配置

`appsettings.json` 的 `Coding` 节（默认 `Enabled: false`）：

```json
"Coding": {
  "Enabled": true,
  "ArtifactDirectory": ".data/artifacts",
  "Grants": ["read", "write", "execute"],
  "RequiredVerification": ["unit_tests"],
  "IgnoredDirectories": ["TestResults"],
  "Profiles": [
    { "Name": "build", "FileName": "dotnet", "Arguments": ["build"],
      "TimeoutSeconds": 180 },
    { "Name": "unit_tests", "FileName": "dotnet",
      "Arguments": ["run", "--no-build", "--", "self-test"],
      "TimeoutSeconds": 180, "MinimumTests": 1,
      "TestCountRegex": "Tests run: (\\d+)" }
  ]
}
```

`IgnoredDirectories` 与工作区指纹共用同一 provider，验证产物目录必须排除，否则“刚通过的证据会被自己写的日志判为过期”。

## 7. 验证

确定性工程验收（脚本化假模型 + 真实临时工程 + 真实文件 + 真实测试进程），离线、不调用真实模型：

```powershell
.\scripts\verify.ps1                      # 全量：V0 回归 + V1
.\scripts\verify.ps1 -Stage v1-e2e        # 仅编码端到端
```

当前 Release 构建 0 警告 0 错误，离线测试 **50/50 通过**（V0 既有 36 + V1 新增 14）。关键 V1 阶段：

| 阶段 | 覆盖 |
| --- | --- |
| `v1-tool` | per-tool 超时覆盖默认上限 |
| `v1-workspace` | 受限读取/搜索/列举、哈希、跳过规则；越界/链接/授权/二进制/大小拒绝无副作用 |
| `v1-mutation` | create 拒绝覆盖；账本只计 Agent 改动；过期哈希与歧义补丁零副作用；唯一补丁原子替换并保留 CRLF |
| `v1-process` | 退出码、双流排空、stderr、启动失败区分；超时杀一次性进程 |
| `v1-verify` | 通过/失败证据绑定真实退出码与 revision；零测试/缺 marker 不发通过证据；运行中变更使证据失效 |
| `v1-e2e` | 失败修复闭环（含编辑失效→重发）；提前声称完成被缺口阻止；新增回归用例被发现并暴露缺陷 |

样例工程 `examples/sample-dotnet-project/` 是零 NuGet 依赖的控制台程序，内置一个种子缺陷（`ApplyDiscount` 按绝对量而非百分比扣减），从 `tests/*.case` 数据文件读取断言，`self-test` 输出 `Tests run: N` 标记并以退出码反映结果。种子态退出 1（第二个用例失败），修正实现后 3/3 通过。**新增回归用例只需添加 `.case` 文件，无需重编译**，对应“新增回归测试”验收。

## 8. G 层真实模型验收（仍需联网执行）

确定性测试证明框架能力，但不能证明模型稳定性。真实模型验收应：启用 `Coding` 并指向样例工程，分别完成（1）修复既有缺陷使现有与回归测试通过；（2）先添加一个能暴露原问题的回归用例再修复。记录原始需求、最终 diff、验证命令、退出码、日志、工作区 revision、模型与工具调用次数，并保留失败尝试——不以一次成功宣称普遍稳定。该步骤消耗模型额度，不在离线 `verify.ps1` 内。

## 9. 已知限制

- 进程树终止在 Windows 上为 best-effort；无法确认时进入核实流程而非假定成功。
- 补丁协议为单处唯一 `old/new` 文本匹配，单次调用不处理多处替换。
- 指纹为非加密快照基线，不提供并发隔离或不可变验证快照（后续强化）。
- 产物目前直接落盘到工作区外目录并登记 `ArtifactReference`，V1 不做独立 blob 服务。
