> Model 决定下一步建议做什么；Harness 决定这一步能否执行、如何执行、如何记录，以及执行后怎样继续。

## 2. 核心认识：动态决策进入固定的运行机制

**架构归纳：** Agent 是一个由程序驱动、由模型反复提供语义决策的反馈系统。

```text
用户输入
   ↓
Harness：记录输入、加载状态、构造上下文与工具清单
   ↓
Model：理解问题，返回文本、工具请求或其他协议输出
   ↓
Harness：解析输出
   ├─ 工具请求 → 校验与授权 → 执行 → 记录结果 → 下一次模型调用
   └─ 结束候选 → 检查待处理输入、停止规则与目标状态 → 继续或结束
```

模型生成工具名称和参数，只是在提出调用请求。真正读取文件、创建进程、修改代码、保存状态的是 Harness 及其执行器。模型接入配置、协议适配、网络请求和重试也属于 Harness。

这里的“模型自发调用”是指：模型依据用户目标、指令、可见工具和当前观察结果，在运行时选择行动。它不是脱离程序自行访问操作系统。

对跨语言开发者，可以这样对应已有知识：

| Agent 概念 | 熟悉的工程概念 |
| --- | --- |
| 模型接入 | 外部服务适配器 |
| 工具调用 | 带参数的命令请求或 RPC |
| 工具路由与执行器 | 命令分发器与处理器 |
| Agent 主循环 | 反馈驱动的状态机 |
| 上下文构建 | 面向一次请求的数据投影 |
| 执行记录与恢复 | 日志、检查点、状态重建 |
| 任务验收 | 业务状态转换的前置条件 |

开发者需要预先实现的是运行规则；解决某个具体问题的步骤，可以由模型在这些规则内动态选择。

## 3. Harness 的六个核心职责

**架构归纳：** 原文的五模块划分仍然成立。这里将持久化与恢复从运行控制中单独展开，以突出长任务中的状态问题。

| 职责 | 核心问题 | 最小实现 |
| --- | --- | --- |
| 模型接入 | 怎样获得可处理的模型输出？ | 请求适配、响应解析、错误分类、受限重试 |
| 上下文管理 | 这次模型应看到什么？ | 指令、历史、工具描述、必要状态、容量控制 |
| 执行管理 | 行动请求怎样变成真实操作？ | 工具注册、参数校验、权限、超时、输出限制、结果关联 |
| 运行控制 | 何时继续、等待或停止？ | 主循环、取消、输入队列、预算、任务状态转换 |
| 持久化与恢复 | 中断以后怎样继续？ | 任务记录、调用与结果、检查点、恢复规则 |
| 目标与验收 | 怎样证明满足了用户要求？ | 目标、约束、完成候选、证据记录、可配置的完成门槛 |

事件记录和可观测性贯穿上述职责。模块数量不是架构优劣的判断标准，职责是否清楚、状态是否有明确归属更重要。

**源码事实：** Codex 的 Node.js CLI 启动器启动本地二进制，TypeScript SDK 也通过子进程接入 Codex。它们不是完整 Agent 核心循环；要学习 Harness，应优先阅读 Rust 核心实现。[S1][S2]

## 4. “硬编码”的准确含义

本文将“硬编码”理解为**程序强制实施的机制**。它可以读取配置、使用策略对象、调用模型辅助判断，但不能仅靠当前执行模型自觉遵守。

可以将控制分为三个层次：

| 层次 | 示例 | 能保证什么 |
| --- | --- | --- |
| 提示词约束 | “修改后请运行测试” | 影响模型选择，不能保证模型必定执行 |
| 结构化表达 | 工具 schema、计划清单、完成状态参数 | 提供明确的表达协议；实际校验仍需程序完成 |
| 程序强制 | 完成入口检查必要测试证据 | 在覆盖到的执行路径中阻止不满足条件的状态转换 |

一段提示词即使写死在源代码里，其中的要求也不自动成为执行保证。

固定的是协议、边界、状态转换和资源约束。动态的是任务拆分、搜索内容、修改方案、行动顺序和失败后的修正策略。

同一能力往往同时包含两者。例如自动压缩：程序检测容量并触发；模型可以生成摘要；程序保存结果、重建上下文并恢复工作。**内部调用了模型，不意味着整个流程由模型自主触发。**

## 5. 能力责任矩阵：五个问题决定控制边界

**设计建议：** 为每项能力回答五个问题：谁触发、谁决定内容、谁执行、保存什么、失败后去哪里。以下是 MiniHarness 的推荐职责分配，不是对两个项目全部实现的逐项声明。

“持久状态”列表示建议保存的信息，不意味着每个流式片段都必须同步落盘；持久化时点应按恢复要求设计。

### 5.1 模型与上下文

| 能力 | 触发者 | 内容决策者 | 执行者 | 持久状态 | 失败去向 |
| --- | --- | --- | --- | --- | --- |
| 下一次模型请求 | 主循环或任务调度器 | 程序组装输入；模型生成输出 | 模型适配器与服务端 | 请求关联 ID、关键输入、完整输出、用量 | 可恢复连接错误受限重试；取消、限额和致命错误停止 |
| 系统指令与环境注入 | 初始化或请求准备流程 | 配置、宿主及用户规则 | ContextBuilder | 指令或配置版本、环境引用 | 必要配置缺失则报错，不让模型猜测权限 |
| 搜索与上下文补充 | 通常由模型请求，也可由固定流程触发 | 模型选关键词与目标；程序按规则补充 | 搜索、文件或检索工具 | 查询、结果引用、来源 | 将可处理错误反馈给模型，允许改查法 |
| 上下文压缩 | 容量策略、用户命令或获准的模型请求 | 模型可生成摘要；程序决定保留结构 | 压缩流程和 ContextBuilder | 摘要、保留状态、压缩边界与后续历史 | 有限重试或受控停止，避免破坏唯一可恢复状态 |
| 规划与重新规划 | 模型判断或用户要求 | 模型提出步骤 | 计划工具及存储接口 | 当前计划、进度及变更 | 参数错误反馈；更新计划不等于工作完成 |

### 5.2 工具与资源

| 能力 | 触发者 | 内容决策者 | 执行者 | 持久状态 | 失败去向 |
| --- | --- | --- | --- | --- | --- |
| 工具注册与暴露 | 启动或配置更新流程 | 程序策略，可结合模型发起的发现请求 | Registry 与工具发现组件 | 工具身份、版本或请求快照引用 | 不可用工具明确拒绝，不执行猜测的名称 |
| 工具调用 | 模型或内部受控流程 | 模型决定名称和参数；程序决定准入 | Router 与具体执行器 | call_id、参数、执行状态、结果 | 可修正错误回填；致命错误进入停止流程 |
| 权限与审批 | 实际操作前的检查点 | 固定策略、用户授权，可结合审查模型 | 权限组件与实际执行环境 | 授权范围、决定、适用调用 | 拒绝或等待授权；不能由执行模型自行放行 |
| 文件修改 | 模型提出补丁或编辑请求 | 模型决定修改内容 | 编辑器、补丁工具或受控 Shell | 改动、相关版本信息、执行结果 | 冲突或前置条件不满足时回填，重新读取和决策 |
| 长命令 | 模型请求或固定验证流程 | 模型或项目配置决定命令 | 进程管理器 | 命令、进程标识、输出位置、退出状态 | 超时、取消、异常退出分别处理；重启后核实进程状态 |
| 工具并发 | 模型提出多调用，程序调度 | 模型表达任务关联；程序实施并发规则 | 调度器与执行器 | 调用关系、各自结果与时序 | 保留部分成功；不得将整批失败直接重跑 |
| 子 Agent | 模型、用户或显式工作流 | 模型可拆分子任务 | 子任务管理器 | 子任务 ID、目标、消息、状态、用量 | 等待、取消、收集部分结果或反馈失败 |

### 5.3 生命周期与交付

| 能力 | 触发者 | 内容决策者 | 执行者 | 持久状态 | 失败去向 |
| --- | --- | --- | --- | --- | --- |
| 网络重试 | 适配器识别可重试错误 | 程序策略 | 模型或工具适配器 | 尝试次数、错误及请求关联 | 达上限后退出；涉及副作用时先核实结果 |
| 业务错误修复 | 模型收到失败观察 | 模型分析原因并改变方案 | 新一轮受控工具调用 | 失败证据、后续动作、修复结果 | 无进展或预算不足时明确停止，不无限自修复 |
| 用户中途补充 | 用户 | 用户表达约束，模型调整策略 | 输入队列和主循环 | 新输入、顺序、已接收状态 | 不丢输入；按中断策略决定何时生效 |
| 取消与等待 | 用户、预算、策略或待回答问题 | 程序决定合法状态；模型可提出澄清问题 | Runner 与资源管理器 | 停止原因、未完成事项、资源状态 | cancelled、waiting_user 等独立状态，不能冒充完成 |
| 重启恢复 | 用户或获准的恢复流程 | 程序重建状态；模型决定恢复后的业务行动 | Store 与 Runner | 检查点、日志尾部、未决调用 | 对不确定副作用先核实，禁止无条件重放 |
| 完成验收 | 模型提出完成候选或固定检查点 | 用户/项目定义要求，模型可补充验证方法 | CompletionPolicy 与验证器 | 要求、证据、代码版本、判定 | 缺口反馈后有限继续，或等待人工判断 |
| 跨轮继续目标 | 显式启用的目标运行机制 | 程序决定是否续跑，模型决定下一轮做什么 | 调度器与 Runner | 目标状态、累计用量、续跑关系 | 预算、取消、阻塞或持续无进展时停止 |

## 6. 固定机制如何连接动态行动

### 6.1 通过结构化协议连接

模型提出请求，例如：

```json
{
  "call_id": "call_17",
  "name": "run_tests",
  "arguments": { "target": "order-idempotency" }
}
```

执行器返回真实观察：

```json
{
  "call_id": "call_17",
  "status": "failed",
  "exit_code": 1,
  "output": "expected inventory=9, actual inventory=8"
}
```

这是教学协议，不是 Codex API 的逐字段定义。关键要求是：调用与结果可关联，失败可表达，进程仍在运行也有独立状态。`call_id` 用于结果关联，本身不提供业务操作的幂等保证。

程序把调用及结果放入下一次模型输入，模型再决定修改实现、修正测试、搜索其他位置或提出问题。

**源码事实：** Codex 在识别完整工具调用项后先记录请求，再排入执行，并设置 `needs_follow_up`；后续收集工具结果写回历史。[S4][S5]

### 6.2 以修改库存接口为例

| 阶段 | 模型动态行为 | 程序固定责任 |
| --- | --- | --- |
| 定位 | 搜索订单和库存实现，选择读取文件 | 执行搜索、控制访问、返回真实内容 |
| 分析 | 判断重复请求可能缺乏幂等保护 | 保存相关历史与工具观察 |
| 修改 | 生成实现补丁和回归测试 | 检查权限与参数、应用补丁、报告冲突 |
| 验证 | 选择相关测试 | 管理进程、输出、退出状态和证据 |
| 修复 | 根据测试失败调整实现或测试 | 新请求再次通过相同执行边界 |
| 完成 | 提出完成判断及证据说明 | 按配置检查完成门槛，保存真实任务状态 |

业务步骤可以变化，执行协议保持一致。程序无需写死“第三步必须检查幂等”；它需要保证模型提出的每一步都经过必要的控制和记录。

### 6.3 约束放在不可绕过的检查点

以下是**设计建议**，不是当前 Codex 所有路径的既有保证：

| 产品要求 | 检查点 | 失败结果 | 状态去向 |
| --- | --- | --- | --- |
| 禁止依据过期内容编辑 | 写入时核验已读取版本或内容前置条件 | 返回冲突及必要信息 | 模型重新读取与决策 |
| 达到任务预算后不再启动新工作 | 请求与工具准入处 | 记录预算限制 | budget_exhausted |
| 必要测试通过才能完成 | 接受完成候选前 | 返回缺失或过期证据 | 继续修复或等待人工处理 |
| 用户取消后停止活动工作 | 取消传播与资源清理边界 | 保存部分结果和未决事项 | cancelled |

检查应覆盖所有相关入口。只限制编辑工具，而允许 Shell 任意写入，不能形成统一的写入约束。文件版本检查本身也要考虑检查与写入之间的并发变化。

## 7. 长任务需要解决的四类状态问题

### 7.1 区分生命周期和四种结束

**源码事实与架构归纳：**

| 概念 | 用途 |
| --- | --- |
| Thread | 可持久保存的工作会话身份与历史 |
| Session | 当前运行中的会话实例、队列、服务和状态 |
| Turn | 一轮工作，可包含多次模型调用与工具调用 |
| Step | 一次模型请求所使用的配置与能力快照 |
| Goal | 可跨轮维护的目标；是否自动续跑取决于功能与宿主规则 |

```text
模型响应结束 ≠ 工具执行结束 ≠ Turn 结束 ≠ 用户目标完成
```

Codex 的 `run_turn` 根据工具后续需求、待处理输入等决定是否继续；停止 Hook 也可能请求继续。Goal 功能启用且满足条件时，可以在空闲状态启动下一轮。[S3][S12]

Codex 的 `StepContext` 保存本次请求使用的配置、工具路由、环境和 MCP 连接等，避免向模型展示的能力与执行时使用的能力无意错配。部分实时授权仍按所属轮次和当前授权处理，不能把它理解成所有权限永久冻结。[S7]

### 7.2 区分三层状态

| 状态层 | 内容 | 不能替代什么 |
| --- | --- | --- |
| 持久任务状态 | 目标、约束、进度、调用记录、验证证据 | 不能直接证明外部资源当前仍是记录中的状态 |
| 当前模型上下文 | 本次请求可见的历史、摘要和工具结果 | 不能作为无限容量或唯一可信的任务数据库 |
| 外部工作现场 | 文件、Git 工作树、进程、数据库、远程资源 | 不能仅靠恢复聊天历史重建 |

**设计建议：** 关键目标、约束和完成证据应保存在可恢复状态中。摘要可以帮助模型接续理解，但不应成为唯一的权限来源或执行事实依据。

### 7.3 区分压缩、检查点、恢复和验收

| 机制 | 解决的问题 |
| --- | --- |
| 上下文压缩 | 下一次模型输入装不下 |
| 恢复检查点 | 中断后从哪里、依据什么继续 |
| 历史恢复 | 重建会话及相关运行状态 |
| 工作目录快照或回滚 | 保存或恢复文件现场；需要单独机制 |
| 验收 | 当前成果是否满足用户要求 |

**源码事实：** Codex 的本地摘要压缩路径会构造替代历史、补回初始上下文与 World State，并重算 token 使用量。历史输入还会规范化调用与输出的关系。[S8][S9]

恢复并不等于重放所有工具。Codex 有专门的历史重建逻辑，daemon 中断恢复也有适用条件；不能由此推断任意外部进程和资源都可无损恢复。[S10][S11]

**设计建议：** 将未决调用区分为“未开始”“已开始但结果未知”“已完成”。外部操作已经成功、结果却未落盘时，先查询外部状态或使用操作级幂等机制，不要直接重复执行。

### 7.4 区分进程等待和任务预算

长命令需要独立管理：

- `yield`：结束本次等待，进程可能继续运行。
- `timeout`：达到某项时间限制，是否终止由具体执行模式决定。
- `cancel`：收到取消信号，按资源所有权和生命周期处理终止或清理。

**源码事实：** Unified Exec 管理交互进程、输出缓冲和相关执行控制。[S6]

两种 token 预算也应分开：上下文容量限制控制单次请求是否装得下，累计任务预算控制整个目标还允许消耗多少。压缩不会让累计成本清零。

**设计建议：** token 使用量存在估算和事后结算，累计预算实现应明确预留、最大输出限制和超额处理；不要将“调用前检查”描述为精确费用绝不超限的充分条件。

## 8. 计划、目标状态和验收不是同一能力

**源码事实：** Codex 的 `update_plan` 处理器解析参数、发送计划更新事件并返回结果。它本身不按照清单自动执行下一项，也不校验某项是否真的完成。[S13]

Goal 更新工具执行状态参数校验、记账和持久化；不能把 `complete` 状态写入成功理解成通用测试验证器已经证明任务完成。[S14]

**设计建议：** 将完成视为候选状态：

```text
模型提出完成候选
    ↓
程序检查必须满足的要求及有效证据
    ├─ 满足 → completed
    ├─ 可修复缺口 → 回填缺口，受预算约束继续
    └─ 需要人工判定或外部条件 → waiting_user / blocked
```

完成证据应关联被验证的代码版本或工作树状态。测试通过后又修改了相关文件，旧结果可能不再证明当前成果。

验收还应区分机器可验证要求和语义要求：测试、构建与格式检查可自动执行；“交互是否符合预期”等要求可能需要人工确认或额外评估。测试全绿只证明覆盖到的内容，不等于用户目标必然全部满足。

## 9. 最小迭代路线：先闭环，再跨边界

**设计建议：** 单 Agent 已能完成长任务；多 Agent、MCP、技能和 Code Mode 可在需要时增加。

| 迭代 | 交付能力 | 固定流程 | 模型动态部分 | 验收示例 |
| --- | --- | --- | --- | --- |
| V0 最小闭环 | 模型适配、工具注册、结果回填、基础日志、取消和上限 | 请求、解析、准入、记录、继续或停止 | 工具选择与参数 | 连续调用工具，再依据真实结果回答 |
| V1 编码闭环 | 搜索、读文件、补丁、测试 | 写入控制、进程执行、错误与输出处理 | 定位、修改、选择测试、修复失败 | 测试失败后能修改并再次验证 |
| V2 长时间运行 | 进程句柄、中途输入、等待与取消 | 资源生命周期与状态转换 | 观察输出、吸收新约束、重新规划 | 长命令期间能处理纠正与取消 |
| V3 跨窗口与重启 | 压缩、持久化、恢复、任务状态 | 压缩触发、保存顺序、恢复边界 | 摘要内容、恢复后的行动 | 强制压缩或重启后仍保留目标和未决事项 |
| V4 可验收交付 | 完成候选、证据门槛、累计预算、无进展处理 | 完成准入和停止规则 | 补齐缺口、解释结果 | 证据缺失或过期时无法误标完成 |
| V5 按需扩展 | MCP、技能、Code Mode、多 Agent | 注册、调度、权限和资源限制 | 组合工具与委派内容 | 用真实任务证明扩展带来的收益 |

这是一条教学顺序，不意味着把可靠性无限推迟。V0 就应保留清晰的状态和存储接口，后续接入持久化；如果产品从一开始就要求无人值守或重启恢复，应提前完成 V3、V4 的必要部分。

无需一开始就建设向量数据库、复杂计划引擎和分布式调度。先用文件搜索、简单任务状态及追加日志，把闭环和失败路径做清楚。

## 10. MiniHarness 的接口与控制骨架

### 10.1 推荐接口

**设计建议：** 这是便于跨语言实现的职责示例，不要求一开始拆成独立服务。

| 接口 | 输入与输出 | 职责 |
| --- | --- | --- |
| ModelProvider | 模型请求 → 结构化响应或事件流 | 协议适配、请求和连接错误处理 |
| ContextBuilder | 任务状态与能力快照 → 模型请求 | 内容选择、容量控制、必要状态注入 |
| ToolRegistry | 工具名称 → 描述和执行器 | 保证可见能力与可执行能力一致 |
| ToolExecutor | 调用及执行上下文 → 结果或运行句柄 | 执行、超时、取消、输出管理 |
| TaskStore | 任务、事件、调用记录 → 可恢复状态 | 持久化和恢复边界 |
| CompletionPolicy | 完成候选与证据 → 完成、继续或等待 | 实施产品规定的完成门槛 |
| AgentRunner | 用户输入与任务状态 → 生命周期推进 | 串联上述接口 |

工具请求至少要有调用身份、名称和参数；结果至少要表达对应调用、状态、输出或输出引用。任务状态要独立表达进行中、等待、取消、失败、预算停止和完成，避免一个布尔值承载全部含义。

### 10.2 教学伪代码

下面省略流式细节和并发优化；错误处理由被调用组件按明确契约完成。

```text
function runTask(taskId):
    state = store.restoreAndReconcile(taskId)

    while true:
        control = consumeUserInputAndCancellation()
        state.recordAcceptedInputs(control.newInputs)

        if control.cancelled:
            cleanupAccordingToPolicy()
            return store.stop("cancelled")

        if budget.cannotStartMoreWork(state):
            return store.stop("budget_exhausted")

        if context.needsCompaction(state):
            summary = model.summarizeWithLimits(state)
            state = context.rebuildPreservingRequiredState(state, summary)
            store.saveCompactionCheckpoint(state)

        request = context.build(state, captureCapabilities())
        response = provider.callWithBoundedRetry(request)
        store.record(response)
        state.append(response)

        if response.hasToolCalls:
            for call in response.toolCalls:
                checkCancellationAndBudget()
                admission = validateAndAuthorize(call)

                if admission.requiresUser:
                    return store.waitForApproval(call)

                if admission.rejected:
                    result = rejectedResult(call.id, admission.reason)
                else:
                    store.recordToolStartedWithRequiredDurability(call)
                    result = executeManaged(call)

                store.recordToolResult(call.id, result)
                state.appendToolResult(call.id, result)

            continue

        if response.requiresContinuation or hasPendingInput():
            continue

        if response.needsUserAnswer:
            return store.waitForUser(response)

        verdict = completionPolicy.evaluate(state, response)

        if verdict.complete:
            return store.complete(response)

        if verdict.canContinue:
            state.appendFeedback(verdict.missingEvidence)
            continue

        return store.stopWithReason(verdict.reason)
```

这里动态变化的是模型输出的方案、工具参数和修复行动。固定的是准入、记录、反馈、取消、预算和完成判定过程。完整实现还需把终止、持久化失败和资源清理放入可靠的异常处理路径。

### 10.3 错误按含义分流

| 错误类型 | 推荐处理 |
| --- | --- |
| 未知工具、参数错误 | 返回结构化错误，让模型修正 |
| 文件不存在、补丁冲突、测试失败 | 保留真实观察，让模型改变业务策略 |
| 瞬时连接错误 | 适配器受限重试，必要时核实已有执行结果 |
| 授权拒绝或待审批 | 拒绝或等待，不能自动绕过 |
| 用户取消、预算耗尽 | 进入对应停止状态，不作为普通业务错误无限回灌 |
| 状态损坏、无法保证记录可靠 | 停止自动执行并明确报告 |

**源码事实：** Codex 的工具分发区分可以反馈给模型的错误与致命错误。因此，“所有错误都转成文本继续循环”只是某些教学实现的简化，不能当作生产原则。[S15]

## 11. 验证与学习方法

将验证分成两类：

| 类型 | 验证对象 | 方法 |
| --- | --- | --- |
| Harness 确定性测试 | 程序是否可靠实施运行规则 | 使用脚本化假模型，预设输出，检查事件、状态与副作用 |
| Agent 任务评估 | 模型能否选择有效行动完成工作 | 使用真实模型和代表性任务，记录成功率、成本、耗时和错误类型 |

建议优先验证这些路径：

1. 工具请求、真实结果和后续模型请求正确关联。
2. 工具参数错误可以修正；取消和预算停止不能被当作普通错误绕过。
3. 长命令返回运行句柄后，能够继续读取、获得最终退出状态并正确清理。
4. 中途用户输入不会丢失，已接受输入能进入后续上下文。
5. 压缩后保留目标与必要约束，工具调用与结果关系仍合法。
6. 在“副作用发生但结果未落盘”的位置模拟崩溃，恢复不盲目重复执行。
7. 测试证据与当前代码不匹配时，完成门槛拒绝通过。

阅读源码时，每次追踪一个问题：为什么继续调用模型、工具如何被分发、权限在哪里检查、历史如何恢复、目标如何跨轮继续。不要只按目录顺序通读。
